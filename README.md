# foodmap

**foodmap** is a tool that turns a food blogger's public Weibo posts into an interactive restaurant map, for people who would rather eat where a blogger they trust actually ate than trust a platform's average rating.

## What it is

Scrape a food blogger's Weibo profile feed, identify geo-tagged restaurants, use AI to extract recommended dishes and visit dates, and generate an interactive map.

## Features

- **Multi-blogger switching**: the top dropdown switches between included bloggers, or pick "All" for a merged view
- **Clustered map**: dense areas collapse into numbered bubbles colour-graded by how many spots they contain, and each marker grows with its own visit count, so frequent spots stand out at a glance
- **Sidebar list**: searchable, with cascading continent/country/province/city filters (derived from reverse geocoding of coordinates — more accurate than posting IP); collapsed by default, with an animated arrow hint at the list button on every page load (until dismissed or you start using the map)
- **Visit-year slider**: dual-handle range selection to show only restaurants visited within a time window
- **Locate me**: computes distances via browser geolocation and lists tasty places nearby
- **Travel route replay**: plays back visits in chronological order — short hops use a car icon along an arced street-level view; long hops switch to a plane icon flying an arced route while the map auto-zooms out to fit start and end; one color per year, and every place passed leaves a small icon behind
- **Continent-colored background layer**: color intensity reflects visit counts per continent, synced with the filters
- **Mobile-friendly**, plus a warm-toned basemap (CSS-filter color grading whose strength adapts to the zoom level)

## Install

Node.js >= 18. Puppeteer is installed by `npm install`; the AI extraction step additionally needs an OpenAI-compatible LLM API.

```bash
git clone https://github.com/alloevil/foodmap.git
cd foodmap
npm install

cp config.example.json config.json         # Optional: pin a Chrome path; auto-detected if left empty
cp ai-config.example.json ai-config.json   # Required for extraction only: baseUrl / apiKey / model
```

Neither config file is committed — only the `.example` templates are — so both copies have to be made before the first extraction run. To just look at the sample data, skip the config entirely and run `node server.mjs`: the two bloggers shipped in `data/` render the full map with no keys and no login.

## Quick Start

```bash
npm install
cp config.example.json config.json        # Optional: specify a Chrome path; auto-detected if omitted
cp ai-config.example.json ai-config.json   # Required: configure your LLM API (OpenAI-compatible)

# 1. Log in to the weibo.com main site (scan the QR code; the cookie is stored locally in cookies.json, isolated from other projects)
node login.mjs

# 2. Find the blogger's numeric UID (open their profile in a browser and read it from the URL, e.g. weibo.com/u/1647375747)
#    Or reverse-look it up via https://weibo.com/ajax/profile/info?screen_name=<nickname> (requires a logged-in cookie)

# 3. Probe first (fetches only 1-2 pages, writes nothing to disk, prints location-field hit stats)
node fetch-posts.mjs --uid <uid> --name <blogger name> --probe

# 4. Fetch the full post history (use --mode full for the first run)
node fetch-posts.mjs --uid <uid> --name <blogger name> --mode full

# 5. Identify restaurants + extract recommended dishes (calls the model configured in ai-config.json)
node extract-restaurants.mjs --name <blogger name>

# 6. (Optional) Reverse-geocode each restaurant's continent/country/province/city, used by the
#    sidebar region filters and the continent background colors; uses the free Nominatim API,
#    rate-limited to 1 request/second, so large datasets take a while
node geocode-regions.mjs --name <blogger name>

# 7. Add the blogger's name to data/bloggers.json (a JSON string array) so the blogger-switch
#    dropdown at the top of the map page lists them and their data shows up in the "All" merged view

# 8. Start the map page (pure static file server, matching GitHub Pages behavior)
node server.mjs
# Open http://localhost:3457/?name=<blogger name> (without ?name= it defaults to the Chen Xiaoqing
# sample data; ?name=all merges all bloggers listed in bloggers.json)
```

## How It Works

1. **Scraping** (`fetch-posts.mjs`): paginates `weibo.com/ajax/statuses/mymblog`, merges incrementally with dedup by post id, and stores to `data/<blogger name>/posts_raw.json` (this raw full dataset stays out of git by default — it's large and contains lots of personal post text unrelated to restaurants).
2. **Location detection** (`normalize.mjs`): the location signal in Weibo posts is mainly the `geo` field (`{type:'Point', coordinates:[lat,lng]}` — **note the coordinate order is reversed from standard GeoJSON**), supplemented by a small number of check-in cards (`url_struct` entries with `object_type==='place'`). Neither carries the restaurant name or dishes — only coordinates.
3. **AI extraction** (`extract.mjs` + `extract-restaurants.mjs`): batches the bodies of location-tagged, non-repost posts to an LLM to judge "is this describing a specific restaurant meal", extracting the restaurant name and recommended dishes; output uses a pipe-delimited line protocol instead of JSON (chat text often contains quotes/newlines, and JSON escaping breaks easily).
4. **Aggregation**: within one blogger's dataset, restaurants with the same name are merged into one entry, with multiple visits sorted by time; the "All" view concatenates each blogger's file as-is, so a name two bloggers both use appears twice (2 such names in the shipped data).
5. **Region reverse-geocoding** (`geocode-regions.mjs`, optional): reverse-geocodes coordinates into continent/country/province/city — more accurate than the poster's IP location at posting time, because a restaurant's actual location shouldn't depend on where the blogger happened to be when posting. No API key needed (Nominatim); results are cached by coordinates to reduce duplicate requests.
6. **Display** (`index.html` + `app.js` + `server.mjs`): Leaflet + the CARTO Voyager warm basemap (no API key, with CSS-filter color grading on top); clicking a marker pops up all visits to that restaurant (date / dishes / quote / link to the original post). `restaurants.json` is the only per-blogger data file the map page consumes (it also fetches `data/bloggers.json` for the switcher), and it's small (tens to hundreds of KB), so it's safe to commit to git for public display.

## When to use it

- You trust a handful of food bloggers and want the places they actually visited and wrote a dish recommendation for, rather than a platform-wide average score.
- You are travelling somewhere and want to see what those bloggers ate in that city — that is what the sidebar's continent/country/province/city cascade is for.
- You want a map you can self-host with the data in your own hands: pure static files, no backend, and the dataset is one readable JSON file per blogger.
- You want to see change over time: the visit-year slider and the route replay show a blogger's eating route across years.

## When NOT to use it

- You want restaurants a blogger only mentioned in plain text. Only posts carrying an official location (geo) tag or a check-in card are collected; the author's local scrape of the Chen Xiaoqing account measured a hit rate of about 18% (1131/6129 original posts), a figure that cannot be recomputed from the repo because `posts_raw.json` is gitignored (see Known Limitations).
- You want a complete restaurant database for a city. Coverage depends entirely on which bloggers you ingest and how many geo-tagged posts they wrote — this is not an exhaustive dataset.
- You do not want to log in to Weibo. The profile-feed endpoints require a weibo.com session that is not shared with other Weibo tools, so `login.mjs` is a separate QR-code login.
- You do not want to involve an LLM. Deciding "is this post describing a specific restaurant meal" and extracting the dishes both depend on one, so without `ai-config.json` you can browse existing data but cannot ingest a new blogger.
- You need branches of one brand merged automatically, or the same place spelled differently across cities to align. Dedup merges only on an exact name match, or a substring match within 500m — a deliberate trade-off, detailed in Known Limitations below.

## Known Limitations

- Only posts tagged with an official "location (geo)" or "check-in card" are included; posts that mention a restaurant in plain text without a location tag are not. Measured hit rate on the Chen Xiaoqing account is about 18% (1131/6129 original posts carry a location signal) — **that number comes from the author's local raw scrape and cannot be recomputed from the repository**, because `data/<blogger>/posts_raw.json` is gitignored. The only committed measurement is `normalize.mjs`'s own probe: 13/25 (≈52%) on a 25-post sample of a test account (2026-07).
- Reposts (retweets) are always skipped — the location information belongs to the reposted author and does not represent the blogger's own visit.
- Restaurant dedup first groups by "exact name match", then merges entries where "one name is a substring of the other and the coordinates are within 500m" (e.g. "柴氏" / "甘家口柴氏"), so different spellings of the same place don't leave two dots on the map. Conversely, different branches of the same brand (e.g. "大董" vs "大董金宝汇店", coordinates a dozen kilometers apart) stay independent — merging by name alone would swallow two real points on the map into one. Different spellings across cities (e.g. "海天总部" vs "佛山海天总部食堂") still won't merge.
- Weibo's profile-feed endpoints require a login session on the weibo.com main site, which is not shared with other Weibo tools/projects; log in separately with `login.mjs`.
- Region reverse-geocoding (`geocode-regions.mjs`) is an optional step; if it hasn't been run, the sidebar region filters and continent background colors simply won't show, without affecting anything else.

| `data/<blogger name>/restaurants.json` | Final structured restaurant data, read directly by the map page, safe to commit publicly                                                                                                                                                                                     |
| `data/bloggers.json`                   | List of included bloggers, driving the map page's top switcher dropdown and the "All" merged view                                                                                                                                                                            |

## Testing

```bash
npm test              # Unit tests (node:test, zero framework dependencies): pure-function pipeline + server path resolution + map-core frontend pure logic
npm run test:coverage # Same as above, with a coverage table (this is what CI runs)
npm run test:e2e      # End-to-end interaction tests: real server + Chrome, pinning interactions that previously had bugs
                      # (filter/search syncing with the map, empty-set replay guard, mobile sidebar yielding, etc.); requires a local Chrome install, not run in CI
```

The frontend is tested in two layers: pure logic that doesn't touch the DOM/Leaflet (formatting, search matching, arc math) lives in `map-core.mjs`, shared verbatim between the browser and `node:test` for direct unit testing; DOM/map interactions are covered end-to-end by `e2e.mjs`. `verify-render.js` is the quicker at-a-glance smoke test (count markers + screenshot), handy to run while developing.

## FAQ

**Where does the data come from?** Entirely from food bloggers' publicly posted Weibo profile feeds: the restaurant coordinates come from the post's official `geo` field or a check-in card, the restaurant name and recommended dishes are extracted from the public post body by an LLM, and the administrative region is reverse-geocoded from the coordinates via Nominatim. Only the final structured result (`restaurants.json`, every visit carrying its source post URL) is committed; the scraped raw post text (`posts_raw.json`) is gitignored because it contains large amounts of personal content unrelated to restaurants.

**Why does the coordinate order need a warning?** Weibo's `geo` field is `{type:'Point', coordinates:[lat,lng]}`, the reverse of standard GeoJSON's `[lng,lat]`. `normalize.mjs` handles the difference during normalization; if you parse the raw data yourself assuming the GeoJSON convention, your points land on the other side of the planet.

**Is the live demo real data or a mock?** Real. It is generated from the public accounts of Chen Xiaoqing (@陈晓卿) and Sui Po (隋坡) — 283 restaurants and 312 visits (data cut 2026-07-23; verified 2026-09-08 in `claims.json`), with restaurant names, dishes and quotes all taken from their public posts. `docs/screenshot.png` is a real capture of the same page, but from an earlier extraction: it shows 264 restaurants / 285 visits for Chen Xiaoqing, where the shipped data now holds 252 / 281 for him. Re-capture it with `node verify-render.js --name 陈晓卿` after `node server.mjs` if you want the image to match the current data.

**Can I host it myself? Does it need a server?** No server. The frontend is zero-build static files: `index.html` plus `app.js` fetch `data/<blogger>/restaurants.json` directly, so GitHub Pages can serve the repository root as-is, running the same code as a local `node server.mjs`. That server is a plain static file server and listens on 127.0.0.1 only unless you pass `--host`.

**How is the frontend tested?** In two layers. Pure logic that never touches the DOM or Leaflet (formatting, search matching, arc maths) lives in `map-core.mjs` and is shared verbatim between the browser and `node:test`, so it is unit-tested directly. DOM and map interactions are covered end-to-end by `e2e.mjs` against a real server plus Chrome, pinning interactions that previously broke; it needs a local Chrome so it is not in CI. `verify-render.js` is the faster smoke check — count the markers, take a screenshot.
